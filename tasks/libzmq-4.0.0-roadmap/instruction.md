# Distributed Messaging Library: Next-Generation Wire Protocol and API Refresh

## Overview

This library provides high-performance asynchronous messaging primitives for
building distributed and concurrent systems. Applications compose named socket
patterns (request/reply, publisher/subscriber, push/pull, dealer/router,
exclusive pair) that transport binary frames over TCP, IPC, and in-process
transports. Historically, its wire protocol has evolved through several ZMTP
revisions and its public C API through a series of gradual renames and additions
as new patterns and options were introduced.

---

## Goals

The upcoming release is a major-version turning point. Our plan is to
land a new wire-level protocol foundation (ZMTP/3.0) together with the
first public consumers of that foundation: a new raw-TCP socket type, a
public base-85 codec that user code can use to serialize binary keys, and
a cleaner context-lifecycle API that separates *shutting down* a context
from *finalizing* it. These pieces are related — the STREAM socket, the
new lifecycle helpers, and the base-85 codec are all first-class users of
the new protocol layer — and they should therefore land together as the
release's main storyline.

Alongside the storyline, several long-standing rough edges are ready to be
cleaned up: two socket options are being renamed to make their semantics
consistent with the rest of the API (with the old names kept as deprecated
aliases), one socket option is being added to give consumers a
"latest-only" pipe, another is being added to let peers announce
themselves on ROUTER-to-ROUTER connections, one transport (`inproc://`)
is losing the historical requirement that a peer must bind before another
peer can connect, and one message-passing helper is being introduced to
send data buffers that outlive the send call without copying them.

Consumers of this library talk to it only through its two public C headers
(`zmq.h` and `zmq_utils.h`) and the shared library that implements them.
All requirements below describe what those headers and that library must
expose after the change. When a design decision is genuinely ambiguous,
follow the conventions that the rest of the header already uses (macro
names in `ZMQ_*` style, functions returning `int` where `0` means success
and `-1` means failure with `errno` set, and so on). Public API additions
must be visible with C linkage so that C programs continue to link
against the library.

The following capabilities are planned for this release:

- **Target 1: Public Base-85 (Z85) codec** — expose the encode/decode functions
  used to turn 32-byte binary keys into printable 40-character strings.
- **Target 2: Context lifecycle refresh (`zmq_ctx_term` / `zmq_ctx_shutdown` /
  thread helpers)** — make the shutdown/finalize split explicit and provide
  portable thread helpers so that programs and examples do not need to depend
  on platform-specific thread APIs.
- **Target 3: Zero-copy `zmq_send_const`** — a new send entry point for buffers
  that outlive the call and therefore need not be copied by the library.
- **Target 4: `ZMQ_STREAM` raw-TCP socket type** — a new socket type that lets
  applications exchange raw byte streams with non-ZMTP TCP peers.
- **Target 5: `ZMQ_CONFLATE` socket option** — a "latest wins" mode for
  send and receive queues.
- **Target 6: `inproc://` connect-before-bind** — allow the connect side of an
  in-process endpoint to be created before the bind side exists.
- **Target 7: Socket-option rename `ZMQ_IPV4ONLY` → `ZMQ_IPV6` and
  `ZMQ_DELAY_ATTACH_ON_CONNECT` → `ZMQ_IMMEDIATE`** — plus a matching
  context-level default for `ZMQ_IPV6`.
- **Target 8: `ZMQ_PROBE_ROUTER` socket option** — announce a peer to a
  ROUTER as soon as a connection is established.

## Target 1: Public Base-85 (Z85) codec

Users who want to distribute binary keys (in particular, 32-byte CurveZMQ
keys generated by other tools) need to embed them in text files, source
code, or command lines. Base-64 wastes characters that are inconvenient
in shell contexts, and base-16 is bulky. The library therefore adopts the
Z85 encoding — a base-85 encoding that uses only shell-safe printable
characters — and exposes it as a first-class public API so that user code
does not have to bundle its own implementation.

Typical usage after this change:

```c
uint8_t key [32] = { /* binary key material */ };
char encoded [41];
zmq_z85_encode (encoded, key, 32);         /* -> 40-char printable text */

uint8_t recovered [32];
zmq_z85_decode (recovered, encoded);       /* -> original bytes */
```

### Requirements

1. **`zmq_z85_encode`** — a C function declared in `zmq.h` that turns a binary
   buffer into a printable Z85 string. It writes the encoded characters into a
   caller-provided destination and null-terminates it. The encoding is a
   proper base-85 (four input bytes become five output characters) and is
   defined per ZMQ RFC 32. The function returns the destination buffer so
   that callers can use it as an expression.

2. **`zmq_z85_decode`** — the inverse operation, also declared in `zmq.h`.
   It reads a Z85-encoded null-terminated string and writes the decoded bytes
   into a caller-provided destination, returning that destination. Five input
   characters produce four output bytes.

3. **Round-trip fidelity** — for any input length that is a multiple of four,
   `zmq_z85_decode (dest2, zmq_z85_encode (dest1, data, N))` must recover the
   original `N` bytes exactly.

4. **Character set** — the encoded output must consist only of characters
   drawn from the Z85 printable alphabet (letters, digits, and a small set
   of shell-safe punctuation, as specified by RFC 32); no NULs, whitespace,
   quotes, or backslashes may appear inside the encoded string.

5. **Symbol visibility** — both functions must be exported from the shared
   library with C linkage; a program that only links against the built
   library (without pulling in library sources) must be able to call them.

## Target 2: Context lifecycle refresh

Historically the library exposed a single `zmq_ctx_destroy` call that both
shut down blocking calls on sockets and freed the context. This conflated two
different responsibilities and made it hard to unblock threads that were
stuck inside `zmq_recv` from a shutdown handler (calling `zmq_ctx_destroy`
would deadlock if any thread still held a socket).

The lifecycle is now split into two explicit steps: *shutdown* (interrupt any
blocking socket calls, without freeing anything) and *terminate* (free the
context after all sockets have been closed). The historical `zmq_ctx_destroy`
name is kept as a compatibility alias for terminate so that existing programs
keep working.

Because the shutdown-then-terminate pattern typically involves spawning
helper worker threads that block inside `zmq_recv`, the library also
grows a tiny portable thread wrapper in `zmq_utils.h` so that user code
and examples do not need to depend on POSIX threads or Win32 threads
directly.

Typical usage:

```c
void *ctx = zmq_ctx_new ();
void *sock = zmq_socket (ctx, ZMQ_PULL);
/* ... hand `sock` to a worker thread that blocks in zmq_recv ... */
zmq_ctx_shutdown (ctx);   /* wakes the worker with an ETERM-class error */
/* ... join the worker, then close its socket ... */
zmq_close (sock);
zmq_ctx_term (ctx);       /* now safe to finalize */
```

### Requirements

1. **`zmq_ctx_term`** — new C function declared in `zmq.h`. It is the new
   canonical name for "finalize the context and release its resources".
   Returns `0` on success and `-1` on failure with `errno` set.

2. **`zmq_ctx_shutdown`** — new C function declared in `zmq.h`. It initiates
   the shutdown of a live context without freeing it: any thread currently
   blocked inside a `zmq_recv`/`zmq_send` on a socket belonging to this
   context wakes up with an error, but the caller may still walk the sockets
   afterwards and close them cleanly. Returns `0` on success and `-1` on
   failure with `errno` set. Calling `zmq_ctx_shutdown` on a context whose
   sockets have not yet been closed must not deadlock (this is the whole
   point of the split).

3. **Backward compatibility** — the legacy `zmq_ctx_destroy` entry point
   must remain exported and must behave equivalently to `zmq_ctx_term`
   for programs that only close their sockets first and never call
   `zmq_ctx_shutdown`.

4. **`zmq_threadstart` / `zmq_threadclose`** — new C functions declared in
   `zmq_utils.h`. `zmq_threadstart` starts a background thread running a
   caller-supplied function `void fn (void *arg)` with a caller-supplied
   `void *arg`, and returns an opaque handle. `zmq_threadclose` waits for
   the thread to finish and releases the handle. The signature of the
   thread-function pointer is captured by a typedef in the same header so
   that user code can declare compatible functions.

## Target 3: Zero-copy `zmq_send_const`

The library's existing `zmq_send` copies the caller's buffer into an
internal message before returning. When the caller is sending a compile-time
constant (a string literal, a static array), this copy is wasted work.
The new entry point tells the library it may reference the buffer without
copying it, because the caller guarantees the buffer's storage outlives any
possible use by the library.

Typical usage:

```c
zmq_send_const (sock, "HELLO", 5, 0);   /* library keeps a pointer, no copy */
```

### Requirements

1. **`zmq_send_const`** — new C function declared in `zmq.h`. It has the same
   parameter shape and return convention as `zmq_send` (socket handle,
   const buffer pointer, byte length, flags), and on success returns the number
   of bytes queued. On failure it returns `-1` with `errno` set.

2. **Wire-observable equivalence** — a message sent with `zmq_send_const` must
   be indistinguishable at the receiver from a message with the same bytes
   sent via `zmq_send`. A round trip through any suitable socket pair
   (PAIR/PAIR over `inproc://`, for example) must yield exactly the bytes
   that were passed in.

3. **Flags** — it must accept the same flag values that `zmq_send` accepts
   in the same positions (`0`, `ZMQ_DONTWAIT`, `ZMQ_SNDMORE`, and their
   bitwise combinations).

## Target 4: `ZMQ_STREAM` raw-TCP socket type

Historically the library only spoke its own ZMTP wire protocol over TCP.
This means users cannot easily use this library to talk to plain, non-ZMTP TCP
services (HTTP servers, custom line protocols, hardware devices, etc.).
The new `ZMQ_STREAM` socket type turns a socket into a *raw* TCP
endpoint: bytes travel exactly as they are handed to `zmq_send` (no framing,
no ZMTP), and the socket multiplexes multiple concurrent TCP connections by
using ZMTP-style two-frame messages of the form `[identity][payload]`.

The receive side gives the application an application-visible connection
identity (the first frame of the incoming message) and the raw bytes that
peer sent (the second frame, possibly empty for a connect notification and
possibly split across `zmq_recv` calls for a large payload). The send side
mirrors this: the caller specifies which connection the bytes should go to
by prepending its identity as a `ZMQ_SNDMORE` frame.

Typical usage as a server accepting a plain-TCP client:

```c
void *stream = zmq_socket (ctx, ZMQ_STREAM);
zmq_bind (stream, "tcp://127.0.0.1:5556");
/* first recv on a new connection yields (identity, empty payload)  */
zmq_msg_recv (&identity, stream, 0);
zmq_msg_recv (&payload,  stream, 0);
/* subsequent recvs on the same connection yield (identity, bytes)  */
/* to send bytes back to that peer:                                 */
zmq_send (stream, zmq_msg_data (&identity), zmq_msg_size (&identity), ZMQ_SNDMORE);
zmq_send (stream, "response", 8, 0);
```

### Requirements

1. **New socket type constant** — `ZMQ_STREAM` is defined in `zmq.h`
   alongside the other socket-type constants. `zmq_socket (ctx, ZMQ_STREAM)`
   must succeed and return a valid socket handle.

2. **Bind and connect over `tcp://`** — a `ZMQ_STREAM` socket must accept
   `zmq_bind` on a `tcp://…` endpoint and act as a listening TCP server
   (accepting any TCP client — including a plain, non-ZMTP client).
   Symmetrically, it must accept `zmq_connect` on a `tcp://…` endpoint and
   act as a TCP client.

3. **Frame layout on receive** — every message read from a `ZMQ_STREAM`
   socket is a two-frame message: the first frame is a per-connection
   identity that uniquely identifies the peer within this socket, and the
   second frame carries the raw bytes received from that peer.
   `zmq_msg_more` on the first frame must return non-zero and on the
   second frame must return zero.

4. **Connect notification** — when a new TCP peer connects to a bound
   `ZMQ_STREAM` socket, the first message the application receives for
   that peer has an empty second frame. This is how the application learns
   a new peer exists (and captures its identity) before that peer has sent
   any bytes.

5. **Frame layout on send** — to send bytes to a specific peer the caller
   emits a two-frame message consisting of `(identity, payload)`, where the
   identity is the identity of the target connection and the payload is
   the raw bytes to write to that TCP peer. Sending must accept
   `ZMQ_SNDMORE` on the identity frame as usual.

6. **ZMTP-agnostic wire** — bytes sent as the payload frame must appear on
   the TCP wire literally, with no ZMTP framing prefix. Symmetrically,
   bytes received from a non-ZMTP peer must appear literally in the
   payload frame (subject to the initial ZMTP greeting that a plain-TCP
   peer sees when connecting *into* this library — that greeting is what allows
   a plain client to be recognized). A raw TCP client that speaks ZMTP by
   hand must be able to complete a message exchange with a `ZMQ_STREAM`
   listener.

## Target 5: `ZMQ_CONFLATE` socket option

For monitoring and telemetry workloads, applications sometimes only care
about the *most recent* value on a socket — older messages, if they have
piled up, are worthless and should be dropped. The library adds a socket
option that toggles this "keep-only-the-latest-message" behavior on both
the incoming and outgoing sides of a socket, sidestepping the usual HWM
back-pressure semantics.

Typical usage:

```c
void *pull = zmq_socket (ctx, ZMQ_PULL);
int one = 1;
zmq_setsockopt (pull, ZMQ_CONFLATE, &one, sizeof one);
zmq_bind (pull, "tcp://127.0.0.1:5555");
/* ... peer PUSHes N messages ... */
zmq_recv (pull, buf, sizeof buf, 0);
/* buf now holds the very last message the peer sent, not the first */
```

### Requirements

1. **New socket option constant** — `ZMQ_CONFLATE` is defined in `zmq.h`
   alongside the other socket-option constants. `zmq_setsockopt (sock,
   ZMQ_CONFLATE, &enabled, sizeof enabled)` where `enabled` is an `int`
   must succeed on socket types where conflate semantics make sense
   (PULL, PUSH, SUB, PUB, DEALER, PUSH — the exact set that the reference
   implementation supports). The option must be set before `zmq_bind`
   / `zmq_connect`.

2. **Latest-wins on the receive side** — when conflate is enabled on a
   receiving socket (e.g. `PULL`), if the peer sends `N` messages faster
   than the receiver reads them, the receiver's very next `zmq_recv` must
   yield the last message sent, not the first one. Older messages are
   discarded rather than queued.

3. **Multi-part interaction** — conflate is a single-message mode: multi-part
   messages are not meaningful under it. It is acceptable for the reference
   implementation to enforce this by simply dropping / not queuing multi-part
   payloads; a solver need not do anything extra beyond making single-frame
   PUSH/PULL round-trips work correctly.

## Target 6: `inproc://` connect-before-bind

The `inproc://` transport is used for zero-copy communication between
threads inside a single process. Historically it required that the peer
that calls `zmq_bind` must do so *before* any peer calls `zmq_connect`,
otherwise the connect would fail with an "endpoint does not exist" error.
This forced applications to sequence their thread startup carefully, which
is awkward in general.

After this change, connecting to an `inproc://` endpoint that has not yet
been bound must succeed; any messages the caller then queues on that
socket are held in the context until the bind side comes up, at which
point they flow across.

Typical usage:

```c
void *ctx = zmq_ctx_new ();
void *connect_sock = zmq_socket (ctx, ZMQ_PAIR);
zmq_connect (connect_sock, "inproc://a");      /* SUCCEEDS (was ENOENT before) */
zmq_send_const (connect_sock, "hi", 2, 0);      /* buffered */

void *bind_sock = zmq_socket (ctx, ZMQ_PAIR);
zmq_bind (bind_sock, "inproc://a");             /* now the queued msg drains */
zmq_recv (bind_sock, buf, sizeof buf, 0);       /* -> "hi" */
```

### Requirements

1. **`zmq_connect` on unbound `inproc://` succeeds** — a call to
   `zmq_connect (sock, "inproc://X")` where no socket has yet bound to
   `inproc://X` must return `0` (as opposed to `-1` with an
   endpoint-not-found errno, which is the historical behavior).

2. **Deferred delivery** — messages sent through such a socket before the
   bind side comes up must not be silently discarded. Once a matching
   `zmq_bind` happens, the pending messages must be receivable on the
   bind side in the order they were sent.

3. **Bind-before-connect still works** — the traditional ordering
   (bind, then connect, then send) must continue to work exactly as it
   did before; this change is purely additive on the connect side.

## Target 7: Option renaming (`ZMQ_IPV6`, `ZMQ_IMMEDIATE`) and IPv6 context default

Two socket options have historically had names that read backwards
relative to the rest of the API:

- `ZMQ_IPV4ONLY` — a boolean that, when *true*, restricted the socket to
  IPv4 only. That is the opposite polarity of the rest of the API, where
  boolean options describe an *enabled* feature.
- `ZMQ_DELAY_ATTACH_ON_CONNECT` — a boolean that, when *true*, delayed
  attaching the pipe on connect. The name described the internal
  implementation rather than the observable behavior.

These two options are being renamed to `ZMQ_IPV6` (a boolean that enables
IPv6 when true, i.e. the opposite polarity) and `ZMQ_IMMEDIATE` (a boolean
whose name describes the observable behavior). The old names are kept as
deprecated aliases so that existing code keeps compiling and behaving
identically.

In addition, `ZMQ_IPV6` also becomes a *context-level* option: a program
that wants every new socket in a context to default to IPv6 no longer has
to touch each socket individually. Its default at context level is `0`
(IPv4-only).

Typical usage:

```c
void *ctx = zmq_ctx_new ();
assert (zmq_ctx_get (ctx, ZMQ_IPV6) == 0);            /* default off */
zmq_ctx_set (ctx, ZMQ_IPV6, 1);                       /* turn on globally */
void *s = zmq_socket (ctx, ZMQ_ROUTER);
int v; size_t sz = sizeof v;
zmq_getsockopt (s, ZMQ_IPV6, &v, &sz);
assert (v == 1);                                      /* inherited */
```

### Requirements

1. **`ZMQ_IPV6`** — defined in `zmq.h` as a socket option. It is a boolean
   `int` option that enables (when non-zero) or disables (when zero) IPv6
   support on the socket. `ZMQ_IPV4ONLY` must remain defined with its
   historical numeric value so that old programs continue to compile.

2. **`ZMQ_IMMEDIATE`** — defined in `zmq.h` as a socket option. It replaces
   `ZMQ_DELAY_ATTACH_ON_CONNECT`, which must remain defined as an alias
   with the same numeric value (either through a `#define` alias or by
   preserving the old identifier). Existing programs using the old name
   must keep compiling and continue to see identical behavior.

3. **Context-level `ZMQ_IPV6`** — `zmq_ctx_get` and `zmq_ctx_set` must
   accept `ZMQ_IPV6` as their `option_` argument. `zmq_ctx_get (ctx,
   ZMQ_IPV6)` on a fresh context must return `0` (IPv4-only by default);
   after `zmq_ctx_set (ctx, ZMQ_IPV6, 1)` it must return `1`. Sockets
   subsequently created from that context must report the inherited
   value through `zmq_getsockopt (sock, ZMQ_IPV6, …)`.

## Target 8: `ZMQ_PROBE_ROUTER` socket option

When a ROUTER socket has just accepted a new peer, the application would
like to be told "there is now a new peer available with identity X" so it
can start pushing work to it *before* that peer has sent a first
application message. Historically the only way to trigger this notification
was for the client to send a dummy message.

The library introduces a new socket option that, when enabled on a
ROUTER/DEALER/REQ *client*, causes the client's very act of connecting to
be advertised to the peer as an empty application message. This lets a
server-side ROUTER discover fresh peers immediately after connection setup.

Typical usage on the *client* side:

```c
void *client = zmq_socket (ctx, ZMQ_ROUTER);
zmq_setsockopt (client, ZMQ_IDENTITY, "X", 1);
int probe = 1;
zmq_setsockopt (client, ZMQ_PROBE_ROUTER, &probe, sizeof probe);
zmq_connect (client, "tcp://localhost:5560");
/* server side now immediately sees an incoming message: identity="X", body="" */
```

### Requirements

1. **New socket option constant** — `ZMQ_PROBE_ROUTER` is defined in
   `zmq.h` alongside the other socket-option constants. It must be
   settable via `zmq_setsockopt (sock, ZMQ_PROBE_ROUTER, &enabled,
   sizeof enabled)` where `enabled` is an `int`, before the socket is
   connected.

2. **On-connect empty message** — when a socket with `ZMQ_PROBE_ROUTER`
   enabled successfully completes a `zmq_connect` to a ROUTER peer, the
   ROUTER peer must observe an incoming message consisting of the
   client's identity followed by an empty payload frame. No further
   messages are synthesized by this option; subsequent traffic is
   ordinary application data.

3. **Compatibility with normal traffic** — after the probe message has
   been observed by the ROUTER, the client and ROUTER can exchange
   messages normally in either direction.

## Completion Criteria

- The two public C headers (`zmq.h`, `zmq_utils.h`) declare all new
  functions, macros, and typedefs listed above, with C linkage.
- The built shared library exports all new functions listed above.
- All existing functions and macros continue to exist with unchanged
  observable behavior; renamed options keep their old names as aliases
  so that programs that use the old names continue to build and run.
- Each target's typical-usage snippet above compiles and runs to
  completion against the built library with the described observable
  behavior.
